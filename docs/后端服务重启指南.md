# 后端服务重启指南

适用目录：`/home/ubuntu/monad_lp`，运行用户：`ubuntu`。在这台 Ubuntu / WSL 的终端执行下面的命令。

## 1. 这次为什么访问不了

2026-10-17 排查时，`8100`、`8545`、`5173` 均没有进程监听：应用服务已经停止，数据库文件仍然存在。机器本次启动时间为当天 `10:38:33`；没有配置应用的 systemd 自启服务，用户的 `Linger=no`。缺少退出前日志，无法确认这次是终端关闭、进程异常还是其他原因造成。

Cloudflare 隧道当时仍在运行，其日志明确记录连接 `127.0.0.1:8100` 和 `127.0.0.1:5173` 被拒绝，说明请求到达隧道后找不到本地应用。

目前的启动入口在 `frontend/package.json`：

```text
npm run dev
  ├── npm run rpc → local-rpc：127.0.0.1:8545
  ├── npm run api → lp-api：0.0.0.0:8100
  └── Vite：0.0.0.0:5173
```

它使用 `concurrently -k`：任意一个子进程退出，其余进程也会被停止。因此只启动网页、只重启隧道，都不能替代恢复这三个进程。

本次已经使用下文的 `monad-lp` tmux 会话恢复服务，日志保存在 `output/runtime/monad-lp.log`。

## 2. 最简单的启动方式：一个终端

```bash
cd /home/ubuntu/monad_lp/frontend
npm run dev
```

保持这个终端运行。出现下面三个信息，表示三个服务已开始监听：

```text
local RPC listening on 127.0.0.1:8545
LP Rust API listening on http://0.0.0.0:8100
Local: http://localhost:5173/
```

短暂出现 `Blocking waiting for file lock on package cache` 是两个 Cargo 进程共享缓存时的等待；本次等待几秒后正常启动。编译期间网页可能暂时出现 `ECONNREFUSED 127.0.0.1:8100`，等 API 完成启动后再检查。

停止整套服务：在这个终端按 **Ctrl+C**。重新运行 `npm run dev` 就是重启。

已有环境不必每次执行 `npm ci`。只有提示缺少依赖、找不到 `concurrently` / `vite`，或更新了依赖锁文件时，才在 `frontend` 下执行 `npm ci` 后再启动。

## 3. 推荐日常方式：tmux 后台运行

tmux 可以让服务在断开 SSH 或关闭当前终端后继续运行；机器或 WSL 重启后，需要重新启动会话。

### 先查看是否已启动

```bash
tmux list-sessions
ss -ltnp '( sport = :8100 or sport = :8545 or sport = :5173 )'
```

如果已有 `monad-lp` 且端口正常，不要再重复启动。查看运行窗口：

```bash
tmux attach -t monad-lp
```

离开窗口但保留服务：先按 **Ctrl+B**，松开，再按 **D**。这里不要按 Ctrl+C，Ctrl+C 会停止服务。

### 没有运行时启动

先确认上述三个端口没有被另一套实例占用，再执行：

```bash
cd /home/ubuntu/monad_lp
mkdir -p output/runtime
tmux new-session -d -s monad-lp -c /home/ubuntu/monad_lp/frontend \
  'bash -o pipefail -c "npm run dev 2>&1 | tee -a ../output/runtime/monad-lp.log"'
```

这就是本次实际验证成功的启动命令。后面的 `tee` 将日志追加到文件中，终端退出后仍可排查。

### 重启已经运行的服务

先给这个会话发送 Ctrl+C：

```bash
tmux send-keys -t monad-lp C-c
```

等几秒，再检查：

```bash
tmux list-sessions
ss -ltnp '( sport = :8100 or sport = :8545 or sport = :5173 )'
```

确认 `monad-lp` 会话已退出、端口已释放后，重新执行上一节的后台启动命令。如果提示没有该会话，先检查端口；空闲时可直接启动。

如果端口仍被占用，按照 `ss` 显示的 PID 确认所属进程，回到原来的终端或进程管理器停止它。不要同时启动多个实例，也不要直接使用 `killall node`，以免停止其他项目。

### 查看日志

```bash
cd /home/ubuntu/monad_lp
tail -n 80 output/runtime/monad-lp.log
```

持续查看用 `tail -f output/runtime/monad-lp.log`；退出 tail 用 Ctrl+C，只会退出查看，不会停止 tmux 中的应用。也可以用 `tmux capture-pane -pt monad-lp -S -80` 查看会话最近输出。

## 4. 判断有没有真正恢复

另开一个终端，依次执行：

```bash
# RPC 服务
curl --noproxy '*' --max-time 10 http://127.0.0.1:8545/healthz

# 后端 API
curl --noproxy '*' --max-time 10 http://127.0.0.1:8100/api/health

# 前端到后端的代理链路
curl --noproxy '*' --max-time 10 http://127.0.0.1:5173/api/health

# 20 池行情
curl --noproxy '*' --max-time 15 http://127.0.0.1:8100/api/monad/prices

# 最优报价：只查询，不签名、不发送交易
curl --noproxy '*' --max-time 30 \
  'http://127.0.0.1:8100/api/selection/quote?amount=0.1&token_in=MON&token_out=USDC'
```

成功标准：

| 检查 | 预期 |
| --- | --- |
| RPC 健康检查 | `{"status":"ok"}` |
| API / 前端代理健康检查 | 包含 `"ok":true` |
| 行情 | `prices` 有 20 项；关注 `status`、`as_of`、`state_block` |
| 报价 | `sourceChainId` 为 `143`、`fresh` 为 `true`，并有 `selected` |

健康检查仅说明进程可以响应，不保证上游 RPC 和行情采集正常。行情接口即使返回 HTTP 200，也要检查时间、区块与 `status`。间隔几秒重复查询，确认来源区块或时间继续推进；价格数字不变不一定代表没有刷新。

网页地址：`http://localhost:5173/`；选池页：`http://localhost:5173/#selection`。从另一台机器访问时，把 `localhost` 换成服务机器的局域网地址。

`--noproxy '*'` 用于让本机请求绕过系统代理，避免请求 `127.0.0.1` 时被错误转发。

## 5. 本机正常，但公网域名打不开

先完成第 4 节，再检查隧道：

```bash
systemctl is-active cloudflared
journalctl -u cloudflared -n 50 --no-pager

curl --connect-timeout 5 --max-time 15 https://lp.chayu123.me/api/health
curl --connect-timeout 5 --max-time 15 https://api.chayu123.me/api/health
```

若 cloudflared 确实停止或日志显示需要重启：

```bash
sudo systemctl restart cloudflared
```

应用和隧道是不同的进程；只重启 cloudflared 不会启动 8100 / 8545 / 5173。本机检查成功、公网失败时，继续排查隧道连接、域名转发和网络。不要因为公网失败而反复重建数据库。

这里访问公网沿用当前终端的网络代理配置。本次直接绕过代理访问公网域名出现 TLS 超时，使用原有代理则能访问；单台机器的出站网络问题不能直接判定为公网服务停止。

## 6. 常见问题

| 现象 | 检查与处理 |
| --- | --- |
| 三个端口都没有监听 | 启动整套服务，查看日志最早出现的错误 |
| 只有 5173，8100 / 8545 尚未出现 | 查看 Cargo 是否仍在编译或等待锁；若进程退出，查看其报错 |
| `Address already in use` / `EADDRINUSE` | 有重复实例。用 `ss -ltnp` 找原进程，停止原实例再启动 |
| Vite 自动改用 5174 | 5173 被占用；隧道可能仍转发到 5173，先处理端口冲突 |
| 8100 正常，报价报错或过期 | 检查 8545、上游 RPC 网络与限流；健康检查不代表上游正常 |
| 行情存在但 `stale` / `unavailable` | 检查采集日志与来源时间，刚启动时等采集刷新，再复查 |
| `unable to open database file` / 缺少表 | 检查执行目录和数据库路径；推荐按本文在 `frontend` 启动 |
| `file is not a database` | 新克隆环境先检查文件是否只是 Git LFS 指针 |
| `database is locked` | 检查是否启动了重复实例或正在进行大规模数据库写入；先停重复实例，再重试 |
| 重启电脑 / WSL 后又不能访问 | tmux 不负责开机自启；重新执行第 3 节，或配置下一节的 systemd 服务 |

数据库位置：`data/lp_screener.db`、`data/lp_price_history.db`、`rpc/data/rpc.db`；行情事件库是 `rpc/data/monad_events.db`。`npm run rpc` 已配置相对路径；不要随意换目录直接运行二进制。重启不需要删除数据库，也不要在服务运行时删除 SQLite 的 `-wal` / `-shm` 文件。

全新克隆环境且数据库仍是 LFS 指针时，在首次启动前执行 `git lfs install`、`git lfs pull` 获取快照。本地已有实际数据库时，不必在每次重启时重复拉取或覆盖数据。

## 7. 可选：配置 systemd 自启与崩溃重启

**本次没有安装自启服务，当前仍由 tmux 运行。** 以后希望减少手动恢复时，可以执行本节。下面配置适用于本机 `ubuntu` 用户及当前目录；换机器要相应修改路径。

先按第 3 节停止 tmux 中的应用，确认三个端口已释放。再创建用户服务：

```bash
mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/monad-lp.service <<'EOF'
[Unit]
Description=Monad LP API, RPC collector and web frontend

[Service]
Type=simple
WorkingDirectory=/home/ubuntu/monad_lp/frontend
Environment=PATH=/home/ubuntu/.cargo/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/bin/npm run dev
Restart=always
RestartSec=5
KillMode=control-group
KillSignal=SIGINT
TimeoutStopSec=30

[Install]
WantedBy=default.target
EOF

systemctl --user daemon-reload
systemctl --user enable --now monad-lp.service
sudo loginctl enable-linger ubuntu
```

`enable-linger` 允许用户服务在未登录时启动并持续运行，需要系统管理员权限。WSL 场景中，仍需 Windows 先启动该 WSL 发行版；这不能让已关闭的电脑或未启动的 WSL 对外提供服务。

配置成功后，日常改用下面的命令，不再同时运行 tmux 版本：

```bash
# 重启
systemctl --user restart monad-lp.service

# 查看状态与日志
systemctl --user status monad-lp.service --no-pager
journalctl --user -u monad-lp.service -n 80 --no-pager

# 停止
systemctl --user stop monad-lp.service

# 取消自启并停止
systemctl --user disable --now monad-lp.service
```

systemd 方式的日志通过 journalctl 查看，不写入前面 tmux 使用的日志文件。配置完成后，再执行第 4 节验证接口。
